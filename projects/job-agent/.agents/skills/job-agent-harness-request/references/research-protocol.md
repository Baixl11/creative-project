# Research Protocol

本文件定义问题拆解阶段的调研规则。目标是避免 Codex 在需求不清、问题复杂或把握不足时直接凭经验实现，也避免把外部方案不加判断地套进当前项目。

## 触发条件

出现以下情况必须先调研，再选择方案：

- 用户需求、问题边界、失败原因、验收标准或非目标不明确。
- Codex 对方案没有十足把握，或存在多个可能实现路径。
- 当前项目证据不足以解释问题根因、运行方式、依赖关系或业务语义。
- 涉及新框架、新库、新平台能力、第三方 API、模型服务、构建工具、Electron/浏览器兼容性、性能、安全或数据一致性。
- 现有实现与常见实践冲突，但不能确认项目为何这样设计。
- 验证失败原因不明确，或错误可能来自 related project、运行环境、依赖版本或配置链路。

## 调研顺序

1. 先做本地调研：读取需求输入、`AGENTS.md`、`ARCHITECTURE.md`、`.harness/environment.yaml`、`.harness/workspace-map.yaml`、相关源码、配置、README、测试、CI 和历史任务文件。
2. 再做项目内搜索：使用 `rg` 查调用方、定义处、错误文案、配置键、命令脚本和相邻实现。
3. 如果本地证据不足，可以使用外部工具检索官方文档、规范、issue、release note 或高质量社区实践。
4. 技术方案优先参考官方文档、项目文档、源码、标准规范和维护者说明；社区文章只能作为经验补充。
5. 调研后必须回到当前项目，结合架构边界、现有风格、运行命令、workspace 相关项目和验证能力选择方案。

## 调研产物

触发调研时，在任务目录写入或更新：

```text
.harness/tasks/<YYYY-MM-DD>/<type>/<short-slug>/
└── research-notes.md
```

`research-notes.md` 至少包含：

- 调研触发原因。
- 本地证据：文件、命令、配置、相关项目和已确认事实。
- 外部资料：来源、链接或可追溯描述、适用范围、时效性风险。
- 候选方案：每个方案的适配点、风险、改动范围、验证方式。
- 选择结论：为什么该方案最适合当前项目。
- 不采用方案：为什么放弃。
- 仍需确认的问题：需要进入 `uncertainty-gates.md` 的问题。

## 外部资料使用规则

- 不得只因为搜索结果靠前就采用方案。
- 不得直接复制与当前项目架构、依赖版本、运行环境或安全边界不匹配的方案。
- 对版本相关、API 相关、构建工具相关、平台能力相关的信息，必须优先确认来源时间、适用版本和当前项目版本。
- 如果外部资料之间冲突，必须记录冲突并以官方文档、源码或当前项目证据为优先。
- 如果仍无法判断正确方案，必须触发 `uncertainty-gates.md`，向用户说明调研结论和需要确认的选择。

## 方案选择标准

选择方案时必须同时满足：

- 能解决用户目标中的可观察问题。
- 与当前项目架构、代码风格、依赖版本、workspace 命令图和验证命令兼容。
- 改动范围最小，避免引入不必要的新依赖；跨项目写入必须遵循 `.harness/workspace-map.yaml`，有 `.harness` 的独立项目先确认，无 `.harness` 的附属子仓库可纳入同一任务。
- 有可执行验证路径；如果无法验证，必须记录原因并进入人工确认或阻塞状态。
- 风险、回滚或降级策略清晰。

## 状态与事件

- 调研开始时，`state.json.current_stage` 仍为 `planner`，`progress.planner` 为 `running`。
- 向 `events.ndjson` 追加 `research_started`。
- 写入或更新 `research-notes.md` 后，向 `events.ndjson` 追加 `research_completed`。
- 如果调研后仍有关键未知项，状态进入 `needs_clarification` 或 `blocked_on_decision`。
- 没有完成必要调研时，不得进入 `coding`。
