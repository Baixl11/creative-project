## 页面 03：问题定义

### 页面目标

说明为什么选择“求职匹配”这个场景，以及用户真实痛点是什么。

### 推荐标题

```text
把模糊的求职判断，变成可解释的匹配证据
```

### 场景痛点

```text
求职者面对一个目标岗位时，常常会遇到四个问题：

1. JD 很长，不知道真正关键的要求是什么。
2. 简历内容很多，不知道哪段经历最能支撑目标岗位。
3. 只能凭感觉判断匹配度，缺少逐条证据。
4. 即使知道有差距，也不知道简历 bullet 应该怎么改。
```

### 产品目标

```text
Job Agent 的目标不是替用户“一键编简历”，而是帮助用户完成投递前的判断和准备：

- 读懂岗位：从 JD 中提取关键要求。
- 找到证据：从简历中定位能支撑岗位要求的经历。
- 判断差距：用匹配分、已匹配项和待补强项帮助用户决策。
- 辅助改写：输出可参考的中文简历 bullet。
- 准备面试：根据 JD 要求生成需要提前准备的问题。
```

### 建议视觉素材

- 左侧放“用户困惑”：JD 很长、简历很散、判断靠感觉。
- 右侧放“Agent 输出”：关键要求、证据句、匹配分、改写建议。

## 页面 04：Agent 工作流

### 页面目标

让非技术面试官也能看懂“Agent 到底做了什么”。

### 推荐标题

```text
不是一次 prompt，而是多步骤任务编排
```

### 工作流内容

```text
输入 JD 和简历
    ↓
读取与清洗多格式文件
    ↓
提取岗位标题和关键要求
    ↓
提取简历中的相关经历
    ↓
逐条匹配 JD 要求与简历证据
    ↓
生成匹配分、缺口和证据解释
    ↓
生成中文简历 bullet 改写建议
    ↓
输出 Markdown 报告和 JSON 结构化结果
    ↓
通过 Web UI 展示给用户
```

### 模块说明

```text
输入层：解决真实文件不标准的问题，包括 PDF、图片 OCR、macOS 文本包和普通文本。

解析层：从 JD 中提取岗位要求，从简历中提取更可能有价值的经历。

匹配层：用中文能力词组和证据选择规则，把 JD 要求和简历句子关联起来。

输出层：同时生成给人看的 Markdown 报告，以及给程序继续处理的 JSON。

展示层：用 Streamlit 做本地 Web UI，让非技术用户可以直接上传文件并查看结果。
```

### 建议视觉素材

- 一张横向流程图。
- 可以配合代码目录截图，展示 `agents / services / utils / tests` 的分层。

### 能力 01：多格式输入


### 能力 03：可解释匹配

```text
匹配结果不只输出一个分数，还会说明每条 JD 要求对应到简历中的哪一句证据。

```

### 能力 04：简历 bullet 改写

```text
项目会把匹配证据转成更适合简历表达的中文 bullet，并区分“当前依据”“建议写法”和“为什么这么改”。

这一步把分析结果从诊断升级为可行动建议。
```

### 能力 05：Web UI 演示

```text
CLI 证明项目能跑通，Web UI 让面试官和非技术用户能快速理解产品价值。
```

```text
问题 05：用户真实上传方式更可能是 JD 截图和 PDF 简历。
```

## 页面 10：局限与下一步

### 页面目标

作品集里要敢于讲限制，这会比“什么都能做”更可信。

### 当前限制

```text
1. 当前匹配机制是规则增强版，不是深度语义模型。
2. 复杂 PDF、多栏排版和扫描件仍可能需要更强的清洗策略。
3. 中文 OCR 质量受截图清晰度影响，本轮真实截图 OCR 暂不作为交付阻塞项。

5. 当前是本地 Web UI，还没有公网部署、用户登录和历史记录。
```

### 下一步规划

```text
短期：刷新作品集截图和演示脚本，完成本轮用户行为验收。

中期：接入真实 LLM，对简历 bullet 做更自然的表达润色，并增加 mock / live 双路径测试。

长期：支持多岗位批量比较、投递优先级建议、面试回答提纲生成和用户反馈闭环。
```

## 2 分钟面试介绍

```text
这个项目叫 Job Agent，是我为了学习 AI 项目完整构建流程做的一个本地求职助手。用户可以输入岗位 JD 和简历，系统会自动读文件、提取岗位要求、提取简历亮点、逐条匹配证据，最后生成匹配分、简历改写建议、面试准备问题、Markdown 报告和 JSON 结构化结果。

我最开始没有直接追求复杂大模型，而是先把 Agent 工作流拆清楚：输入层负责处理 TXT、PDF、截图 OCR 和 macOS 文本包；解析层负责提取 JD 要求和简历经历；匹配层负责用能力词组和证据选择规则建立 JD 与简历之间的关系；输出层负责生成中文报告、结构化 JSON 和 Web UI 展示。

真实测试时，我遇到了几个问题，比如中文 JD 匹配分一开始只有 18/100、PDF 简历断行导致证据句不完整、联系方式会被误识别为简历亮点、OCR 后中文字符之间有异常空格。每个问题我都做了对应修复，包括中文能力词组、中文章节识别、PDF 清洗、联系方式过滤和 OCR 文本清洗。现在公开中文样例可以得到 94/100，并且能对 6 条 JD 要求定位简历证据。

为了保证它不是一次性 demo，我还加了高、中、低 3 组评测样例和 61 个 unittest。当前项目默认 mock 模式，可以零成本本地演示；后续如果 API 配置稳定，可以接入真实 LLM 做更自然的简历 bullet 润色和语义判断。
```
